# AGENTS.md

Правила для ИИ-агента, работающего в этом репозитории. Читай целиком перед каждой задачей.
Код, идентификаторы, комментарии к коду и сообщения коммитов: на английском. Общение с владельцем: на русском.

## 1. О проекте

Планировщик задач для Telegram: **бот** (aiogram) + **Mini App** (React) + **REST API** (FastAPI).
Функции: задачи (с матрицей срочность/важность), трекер привычек (таблица с галочками),
психологическая рефлексия (заметки на тему, итоги дня), напоминания
(накануне дедлайна, утреннее планирование, вечерние итоги).

Владелец: фронтенд-разработчик, бэкенд знает поверхностно. Поэтому:
- объясняй нетривиальные решения в 1-3 предложениях в итоговом отчёте;
- не усложняй: простое и читаемое решение лучше «гибкого»;
- если требование неоднозначно, остановись и задай один конкретный вопрос.

Источник планов и порядка задач: `docs/PLAN.md`. Делай **только ту задачу, которую просили**.
Схема БД: `backend/core/models.py`. Менять её можно только вместе с миграцией (см. §5).

## 2. Стек

Python 3.12, asyncio везде. FastAPI, Pydantic v2, SQLAlchemy 2.0 (async, asyncpg), Alembic,
PostgreSQL 16, Redis (rate limiting, при необходимости FSM), aiogram 3, APScheduler 3,
OpenAI API (только генерация тем рефлексии), pytest + pytest-asyncio, ruff.
Фронтенд (`web/`): TypeScript, React, Vite, MobX (клиентское состояние), TanStack Query (серверные данные).
Фронтенд не трогай, пока явно не попросят.

Зависимости: `backend/requirements.txt` (версии зафиксированы). Новую зависимость добавляй
только если без неё нельзя, и упоминай в отчёте.

## 4. Архитектура и правила слоёв

Направление зависимостей: `api` и `bot` -> `core`. **`core` не импортирует `api`, `bot`, `fastapi`, `aiogram`.**
`api` и `bot` не импортируют друг друга.

```
Router (FastAPI) -> Schemas (Pydantic) -> Facade -> Repository -> PostgreSQL
```

**Router** (`api/routers/`): разобрать запрос, получить зависимости (auth, rate limit, сессия),
вызвать один метод фасада, вернуть схему ответа. Никакого SQL, никаких бизнес-правил, никаких `if` по квотам.

**Schemas** (`api/schemas/`): валидация входа и DTO выхода. Правила: `model_config = ConfigDict(extra="forbid")`,
`max_length` для каждой строки, диапазоны для чисел, даты в разумных границах. ORM-объекты наружу не отдавать:
только через response-схему.

**Facade** (`core/facades/`): вся бизнес-логика. Один фасад на домен (`UsersFacade`, `TasksFacade`,
`HabitsFacade`, `ReflectionsFacade`, `NotificationsFacade`), не god-object. Фасад:
- принимает `user_id` в каждом методе и **всегда** ограничивает данные этим пользователем;
  чужой или несуществующий объект даёт `NotFound` (не `Forbidden`, чтобы не раскрывать существование);
- проверяет квоты из `core/limits.py` (при создании сущности блокирует строку пользователя
  `SELECT ... FOR UPDATE`, чтобы параллельные запросы не обошли лимит);
- владеет транзакцией: делает `commit`, при ошибке откат;
- бросает доменные ошибки из `core/errors.py` (`NotFound`, `QuotaExceeded`, `Conflict`, `InvalidInput`).

**Repository** (`core/repositories/`): только запросы к БД. Не делает `commit`, не знает про квоты и правила.
Связанные данные грузятся явно (`selectinload`/`joinedload`), в моделях стоит `lazy="raise"`.

**Маппинг ошибок в HTTP** (в одном месте, `api/main.py`): `NotFound` 404, `Conflict` 409,
`QuotaExceeded` 409 с `code="quota_exceeded"`, `InvalidInput` 422, rate limit 429.
Тело ошибки: `{"code": "...", "message": "..."}`. Stack trace и SQL-ошибки наружу не отдавать.

**Бот** использует те же фасады из `core` напрямую (не ходит в API по HTTP и не пишет SQL).

## 5. База данных

- Только PostgreSQL через SQLAlchemy async. SQLite и `aiosqlite` в проекте не используются
  (в репозитории остались от прототипа: удалить вместе с `planner.db`).
- Схема меняется только через Alembic: `alembic revision --autogenerate -m "..."`, затем **вручную
  перечитай сгенерированный файл**: autogenerate пропускает часть ограничений и переименований.
  Не редактируй применённые миграции, создавай новую.
- FK ссылаются на `users.id` (внутренний ключ). `users.tg_id` используется только для поиска пользователя
  при авторизации.
- Все `created_at`/`updated_at`/`completed_at` хранятся в UTC (`timestamptz`). Календарные даты
  (`deadline`, `checked_on`, `entry_date`, `for_date`) определяются по таймзоне пользователя
  (`zoneinfo`) в фасаде.
- Ограничения целостности (CHECK, UNIQUE, FK, NOT NULL) обязательны на уровне БД, а не только в коде.
- Каждый list-запрос: индекс под фильтр и обязательные `limit`/`offset` (по умолчанию 50, максимум 100).

## 6. Безопасность и защита от злоупотреблений

Источник истины по лимитам: **только бэкенд**. Фронтенд лишь улучшает UX.

- **Авторизация Mini App**: клиент шлёт `initData` на `POST /api/v1/auth/telegram`. Бэкенд проверяет подпись:
  `secret = HMAC_SHA256(key="WebAppData", msg=BOT_TOKEN)`, `hash = HMAC_SHA256(secret, data_check_string)`,
  сравнение через `hmac.compare_digest`, `auth_date` не старше `INITDATA_MAX_AGE` (по умолчанию 1 час).
  Затем upsert пользователя по `tg_id` и выдача JWT (30 мин). Все остальные эндпоинты требуют JWT.
- `user_id` берётся **только** из JWT, никогда из тела запроса, query или пути.
- Квоты (значения в `core/limits.py`, не хардкодить в других местах): активных задач на пользователя,
  привычек, рефлексий, максимум страницы, размеры текстов.
- Rate limiting: slowapi + Redis, ключ по `user_id` (для неавторизованных по IP). Отдельный строгий лимит
  на `/auth/telegram`. Ограничение размера тела запроса.
- Галочки привычек идемпотентны: `UNIQUE(habit_id, checked_on)`; повторная установка не ошибка.
- Дата галочки: нельзя в будущем, нельзя старше разумного окна (см. `limits.py`).
- CORS: только origin Mini App из конфига.
- **Никогда не логируй**: токен бота, JWT, `initData`, ключ OpenAI. Секреты только из env, `.env` в `.gitignore`,
  `.env.example` без значений.
- SQL только через SQLAlchemy с параметрами, никакой конкатенации строк.

## 7. Бот и шедулер

- aiogram 3, long polling, один процесс бота. **Шедулер запускается ровно в одном экземпляре.**
- Роутеры: все функциональные хэндлеры работают только в приватных чатах (`F.chat.type == "private"`).
  **Catch-all роутер подключается последним** и отвечает на любые необработанные апдейты (текст, стикеры,
  фото, голос, колбэки) вежливой подсказкой и кнопкой «Открыть планировщик».
- Middlewares: глобальный перехват ошибок (логируем, пользователю короткое «что-то пошло не так»),
  throttling.
- `TelegramForbiddenError` при отправке: пометить `users.is_active = false`, не ретраить.
- `/start`: upsert пользователя через `UsersFacade`, ответ с кнопкой `WebAppInfo(url=WEBAPP_URL)`.
- **Шедулер**: одна периодическая задача раз в минуту. Выбирает пользователей, у которых в их таймзоне
  сейчас время утреннего/вечернего напоминания (или час напоминания о дедлайнах), и отправляет сообщение.
  Идемпотентность через `notification_log`: сначала `INSERT ... ON CONFLICT DO NOTHING` по
  `(user_id, kind, for_date)`, отправляем только если строка вставилась, затем обновляем статус.
  Не создавай отдельный job на пользователя.
- Рассылки: пауза между сообщениями (лимит Telegram ~30 сообщений/сек), ошибки одного пользователя
  не прерывают остальных.
- **LLM (OpenAI)**: только генерация тем рефлексии пачкой в фоне, результат в таблицу `reflection_topics`.
  Таймаут, ограниченное число ретраев, дневной лимит запросов, резервный статический список тем.
  В промпт **никогда не попадают пользовательские данные**. Падение API не должно ломать ничего,
  что видит пользователь.

## 8. Тесты и качество

- `pytest` + `pytest-asyncio`, **реальный PostgreSQL** (отдельная тестовая БД из docker-compose), не SQLite и не моки репозиториев.
- Каждый метод фасада покрыт: счастливый путь, чужой объект (изоляция пользователей), превышение квоты,
  невалидный вход. Для API: auth (нет токена, просроченный, подделанная подпись), 404/409/422/429.
- Для шедулера: идемпотентность (двойной запуск не даёт дубль), границы таймзон.
- Перед завершением задачи: `ruff check .`, `ruff format .`, `pytest` проходят.
- Типизация обязательна для публичных функций. Без `print`: используй `logging`.
- Маленькие функции, без преждевременных абстракций, без мёртвого кода и закомментированных кусков.

## 9. Как работать над задачей

1. Прочитай этот файл, `docs/PLAN.md` и затронутые модули.
2. Делай минимальный вертикальный срез в рамках задачи. Не рефакторь чужие области «заодно».
3. Не меняй `core/models.py`, `core/limits.py` и публичный API-контракт без явного указания в задаче;
   если считаешь, что нужно, предложи изменение в отчёте.
4. Коммиты мелкие, сообщения в формате `feat(tasks): add create endpoint`.
5. Итоговый отчёт (коротко): что сделано; список изменённых файлов; как запустить и проверить;
   что осталось нерешённым или вызывает сомнения; какие допущения приняты.
